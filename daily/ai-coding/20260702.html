每位 GitHub 维护者本周都应启用的 6 项安全设置

#安全设置 #GitHub安全 #Secret Scanning #AI编码安全 #分支保护 #Dependabot · 来源：GitHub Blog

GitHub Security Lab 推出免费的 Protect Your Project 引导流程，帮助维护者在 30 分钟内完成 6 项关键安全设置：(1) 添加 SECURITY.md 安全策略文件；(2) 启用私密漏洞报告（PVR）；(3) 开启 Secret Scanning + Push Protection——据 GitGuardian 报告，AI 辅助提交的密钥泄露率是基线的 2 倍，2025 年公有仓库新增 2865 万条密钥泄露；(4) 启用 Dependabot 和依赖审查，将不透明的 package.json diff 变为两分钟审查；(5) 开启 CodeQL 代码扫描，一键检测 SQL 注入等安全模式；(6) 在默认分支启用分支保护，要求 PR 审批后才能合并。

推荐理由：对所有使用 AI 编码代理的开发者来说，本文是必读——特别是 Secret Scanning 和分支保护两项。AI 编码代理提交代码时密钥泄露率是人工的 2 倍，启用 Push Protection 可在推送前拦截。分支保护确保 AI 代理的代码变更经过人工审查，防止「失控代理」直接合并到生产分支。建议立即按照文中的 Protect Your Project 流程逐项启用。

GitHub 如何维护开源依赖的许可证合规性

#许可证合规 #开源依赖 #GitHub Enterprise #供应链安全 #Ruleset · 来源：GitHub Blog

GitHub 内部开源项目办公室（OSPO）分享如何使用新推出的 GitHub License Compliance 功能管理数千个开源依赖。该功能通过 Ruleset 机制在 PR 中自动扫描新依赖的许可证，若不符合组织策略则发出告警。开发者可请求豁免，由合规团队审批——支持企业级和仓库级两种策略粒度，支持通配符匹配包例外。GitHub OSPO 先用 Evaluate 模式试运行一个月不阻断合并，确认无误后切换到 Active 模式。该功能面向 GitHub Enterprise Cloud + GHAS 用户。

推荐理由：AI 编码代理在生成代码时经常自动引入新依赖，许可证合规是企业团队必须关注的风险。虽然 License Compliance 功能需要 GHAS 许可，但其策略管理模式——Evaluate 先行、渐进激活、分层审批——值得所有团队借鉴。对于使用 AI 编码代理的团队，建议在 CI/CD 中加入依赖许可证检查步骤，防止 AI 引入许可证不兼容的包。

为什么意图预测需要的不仅仅是 LLM

#LLM局限 #行为预测 #AI编码反思 #Agentic #开发者能力 · 来源：Stack Overflow Blog

Stack Overflow 播客对谈 Yobi CTO Frank Portman，探讨 LLM 在行为预测和意图识别方面的局限性。核心观点：(1) 下一个 token 预测的归纳偏置不适合行为预测——LLM 在综合信息和代码生成方面出色，但在不确定性下的决策能力不足；(2) Yobi 构建「行为基础模型」，使用大规模 Transformer + 图神经网络，处理比语言 token 多三个数量级的行为数据；(3) LLM 在编码和个性化助手两个场景已展现经济价值，但真正需要「决策」的场景（如广告预算分配）仍远超其能力；(4) 代理编码如果使用不当，会「钝化」开发者的深度思考能力。

推荐理由：本文对 AI 编码工具选型有重要参考价值。Frank 指出 LLM 在编码场景的价值主要来自「在上下文中综合信息」而非「决策能力」——这意味着 AI 编码代理适合执行明确任务，但在架构设计等需要判断力的场景仍需人类主导。播客中关于「代理编码会钝化开发者」的讨论值得团队警醒，建议建立 AI 辅助编码的使用边界和审查机制。
