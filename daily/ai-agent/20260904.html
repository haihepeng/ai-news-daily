2026 年最好的多代理架构诞生于 1975 年：黑板模型与 Actor 模型为何卷土重来

#多代理 #黑板架构 #Actor 模型 #互操作性 #Mozaik · 来源：

开源多代理运行时 Mozaik（TypeScript）团队复盘：1975 年卡内基梅隆的语音识别系统 HEARSAY-II 采用的黑板（blackboard）架构——多个独立专家围着一块共享黑板，无人指挥、看到自己能处理的内容就上前书写、解决方案自然涌现——正是当下多代理系统的最佳形态；1973 年 Carl Hewitt 提出的 Actor 模型（私有状态 + 邮箱 + 发消息/创建 actor/决定对下一条消息的行为三种能力）则定义了机制。黑板系统八十年代兴盛后消亡，原因是专家需手工编程、成本过高——而 LLM 就是迟到了五十年的'专家'。作者将互操作性提炼为公式：互操作性 = 并发 × 感知 × 适应。并用自研的 baro 自动软件工厂（规划、架构、批评、故事代理共用一个事件总线，每日在自己仓库上运行）验证：8 个代理并行不阻塞、代理在总线上询问文件归属并自行协商边界、架构代理能发现目标前提错误并上报。文章也坦诚给出待解问题：执行强制、代理加入退出、显式契约与'什么时候 3 个代理不如 1 个'的协调经济学。

推荐理由：以'1975 年的架构 + 2026 年的 LLM'重构多代理设计第一性原理，公式化提炼互操作性三要素并附实战验证，观点有冲击力。

营销自动化公司 Conversion 公开其 text-to-query 代理的架构与评测闭环：让用户用自然语言描述受众（如'最近 30 天提交过演示表单、所在软件公司有 5 万美元以上开放商机的联系人'），代理需理解业务语义、遍历 联系人→公司→商机 关系并生成可编辑的筛选条件。最初直接让模型产出生产级查询语言，只有 Claude Opus 级别模型可靠，且简单查询耗时约 45 秒。他们的解法：给代理少量工具（搜索字段、查历史值、解析业务资产）；创造'更小的语言'——面向模型的受限中间表示（IR）+ 确定性编译器负责完整格式；并构建语义基准 Statement Bench（100 题）驱动评测闭环。最终 8 模型实测：GLM 5.3 Flash 语义正确率 97%、中位延迟 2.34 秒、每千请求成本 1.33 美元（约为 Claude Opus 5 的 1/20）；而 Gemini 3.8 Flash 因 30 秒超时内无法完成多数用例、正确率仅 76%。教训：模型擅长消除歧义、代码擅长保证精确，失败多源于让模型两者都做；'失败已从答错变成答得慢'，推理 token 远超工具调用开销。

推荐理由：提供'受限 IR + 确定性编译器 + 语义基准'的完整 agent 评测与优化闭环实战数据，是构建高性能 NL-to-query 系统的稀缺参考。

MCP 服务器不告诉代理返回值结构？Blacksmith 用'肌肉记忆'缓存让 code mode 提速一倍

#MCP #编码代理 #schema 推断 #上下文优化 · 来源：

Blacksmith 团队记录其通用编码代理 code mode 的优化历程：code mode 把 MCP 工具当作 TypeScript 代码而非 JSON schema 交给模型（模型训练过海量 TS），让代理在沙箱里用一个小脚本完成'调用-等待-再调用'循环，只把结果摘要带回上下文。首次实测却输了：大多数 MCP 服务器只发布输入 schema，list_issues(input): unknown 让模型不得不猜测返回结构，猜错三次浪费三个整轮。但即便输了，code mode 上下文仍更小（起步省 9k token，全程 60.1k vs 101.1k）且更便宜（$1.91 vs $2.01）。他们的解法是 Muscle Memory：运行时从每次 MCP 调用的真实结果推断小型 schema（只记字段名与宽泛类型，不记值），跨调用合并、跨会话持久化，下次工具搜索时直接提供给模型。复赛结果：warm code mode 56.6 秒、6 轮、$1.06，比冷启动快一倍、比经典循环快 27% 且便宜近一半——同一问题同一答案。

推荐理由：揭示 MCP 生态'只有输入 schema、没有返回 schema'的结构性缺陷，并给出基于结果推断 schema 的优雅解法，对 agent 工具链设计有普适启发。

Skills 还是 MCP 工具？按'可审计性 × 灵活性'两轴选型

#Skills #MCP #选型 #可审计性 · 来源：

LogRocket 博客提出选择 agent 能力载体（Skills 与 MCP 工具）不应看特性对比表，而应放在'可审计性 × 灵活性'两轴上思考：MCP 工具暴露固定输入/输出 schema，代理唯一决策是'何时调用哪个工具'，调用可追踪可复现，偏向可审计一端；Skill 则注入自然语言指令，由代理运行时自行判断哪些指引适用、如何执行，解释空间大（可承载固定 schema 无法表达的判断力），但指令可能被误读、相同输入两次运行可能分叉，偏向灵活一端。机制上 Skill 通过渐进式披露只加载名称与描述、命中才读正文，可携带近乎无限的指引而空闲成本极低；MCP 2026-07-28 规范取消 initialize 握手与会话 ID 固定，请求自描述、可落在任意负载均衡实例后，消除了此前 MCP 的重量级负担。作者用同一能力（git 提交区间变更日志生成器）分别以 MCP 工具与 Skill 各实现一次做对照，展示 stateless MCP server 的构建（含防注入的 assertRef 守卫、分隔符技巧与 structuredContent 输出）。

推荐理由：把 Skills vs MCP 的选型争论升维到'可审计性/灵活性'光谱并提供对照实现，是 agent 工具设计决策的实用参考。
